# Phase 4 data contract (schema 1)

V6 only. Generated by `scripts/gen_items.py`; V5 inputs stay unchanged. Consumers
must reject unknown schema, duplicate identities, missing references, unsupported
capabilities and hash mismatch. No TOML floats. V6 skills are generated into `skills-phase4/` through
`gen_skills.py` Phase4 capability analysis; `skills/` remains V5-only. All decimals are exact strings
accepted by Fraction (plain decimal or reduced `numerator/denominator`); integers
are TOML signed integers, checked against the consumer's declared width.

Every TOML root has `schema: int = 1`, `sources: Source[]` and the arrays below.
Source = `{repository: string, revision: string, file: string, lines: string,
symbol: string}`. Paths are repository-relative. Every projected row has `source`.
Lossless XML Node = `{tag: string, attributes: map<string,string>, text: string,
line: int, xml_ordinal: int, children: Node[]}`. Namespace schema attributes are
excluded; comments are not executable nodes. Child order and lexical values are
preserved. `raw: Node` carries all source fields alongside each typed projection;
unknown raw semantics must never be silently treated as executable.

  item/enchant4/set/shield/enchant6/passive/active/trigger context.

## Hash contract

The engine's full Phase4Rules hash uses the accepted design §1.2 typed,
length-delimited encoding, domain `nightfall.phase4.rules.1\0`, plus its Phase3
bundle hash. The generator's `data_sha256` is a reproducibility check, **not a
replacement for that runtime hash**. It hashes UTF-8 canonical JSON (sorted map
keys, compact separators, ensure_ascii=false), preceded by the same domain.
Normalize decimal strings to reduced `n/d` for projected `value`, `chance`,
`bonus_rate`, weight/tax rates and angle bounds. Exclude provenance (`source`,
`sources`, `line`, `lines`) from semantic hashes; preserve semantic raw XML (stripping its provenance) where
no typed projection yet represents the complete input;
include all projected properties, conditions, source ordinals, capability
blockers, angle bounds, formula/policy/blacksmith/tax inputs. Keep arrays ordered.
`rules_manifest.toml` lists every other TOML file alphabetically with its semantic
SHA-256; data hash hashes that ordered list, formula_revision, skill_bundle_sha256 and profile_bundle_sha256.
The profile bundle hashes parsed `classes-phase3/*.toml` and `tables-phase3/*.toml`
by sorted relative path; runtime still includes its full Phase3Rules hash as specified
by the design. The skill bundle
hash lists committed Phase4 skill definitions by ascending ID and hashes their
parsed semantics. File byte hashes and every source item/file:line are recorded
separately in `source_inventory.json`; committed counts/blocker changes are in
`capability_counts.json`. Neither diagnostic JSON is a runtime hash input.

V6 skill conditions retain the existing normalized condition nodes and add
`using_slot {slot:string}`, `player_weight/player_invSize {value:int}`,
`player_resting/player_standing/player_moving/player_running/player_canEscape/
player_flyMounted {value:bool}`, and `player_inside_zone_ids {zone_ids:int[]}`.
`target_type="NONE"` is admitted only for static (`isMagic=2`) definitions with
no effects in any section: these are source item-selector no-ops (e.g. support
skill2515). It never admits targetless damage/buffs. EnchantScrolls is an explicit
selection handler for EnchantItem, not a missing cast effect. Sample286 carries
`sample:out_of_scope` in both its V6 definition and capability row.

`storable` is false for excluded Common/shadow/time-limited/NPC-only/pet contexts;
V6 has no lifecycle/owner state for those items. Unsupported ordinary equipment
effects or starter-extra uses remain storable while equip/use fails closed.

`properties.change_weaponId` is preserved conversion metadata. It is read only
by the deferred ConvertItem skill/ConditionChangeWeapon path, not ordinary equip,
enchant or SA exchange. `capacities.policy.weapon_conversion` explicitly defers
that skill mechanic; it does not defer an otherwise complete weapon template.

Architect D27/D31: V6 rules and skill definitions are hash-referenced from
build-embedded data; snapshots/records carry hashes, not rule bodies. Runtime
must verify the content hash before admission/replay. Generator per-file semantic
hashes remain unchanged by this transport decision. D33 preserves pinned disabled
Mana Potion support in capacities.policy.mana_potion_support.

Revision 2: `Item.etcitem_type` is the effective Java type: EtcItems with
SOULSHOT/SUMMON_SOULSHOT/SUMMON_SPIRITSHOT/SPIRITSHOT default actions are SHOT
(`L2EtcItem.java:51-55`). Literal XML remains in `properties` and `raw`.
V6 conditions additionally encode `player_level_range {ranges:{minimum:int,
maximum:int}[]}` with one inclusive range per skill rank, expanded from literal
or table values. Rank is one-based; the evaluator rejects missing/out-of-range
ranks, then tests `minimum <= player.level <= maximum`
(`ConditionPlayerLevelRange.java:41-43`). D34 keeps `cond:player:levelRange`
blocked until Z publishes executable support; representation alone does not
promote skills/items. Existing fields and V5 condition representations retain
their meaning. D27 per-file hash fields and ordering are unchanged.

Diagnostic `capability_counts.json.required_condition_closure` records
`condition:string`, `architect:string`, `runtime_support:string`,
`skill_ids:int[]`, `template_ids:int[]`, `imported/admitted/deferred:int` for the
D34 required elixir closure. This JSON remains outside semantic runtime hashes.
