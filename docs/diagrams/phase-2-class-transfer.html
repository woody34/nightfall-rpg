Class transfer lifecycle

Step sequence and order: The class transfer workflow executes in seven strictly ordered stages across four system domains (API/Transport, Live Zone Actor, Durable JetStream Replay Log, and Postgres Persistence):

1. ChangeClass gRPC request enters GameService.ChangeClass. The caller's AccountId is authenticated and the CharacterId and IdempotencyKey are validated and parsed.

2. Offline account-scoped frozen receipt lookup: Before routing to live actor state, the persistence ledger checks for an existing receipt matching (account_id, idempotency_key, fingerprint). If the key matches the same request body, the original frozen ChangeClassResponse is returned immediately without live zone involvement. If the key is reused with a conflicting body, the request is rejected with IdempotencyConflict.

3. Live actor preflight: For an unknown receipt, the API routes the command to the live zone actor. Before drafting, the actor rechecks the account-wide receipt and the required checkpoint lane. It admits at most one new transfer per tick while preserving command order; known receipts resolve without a new transfer.

4. Immutable draft, guards and deterministic execution: The actor builds an AppliedTickDraft, then ZoneState::run_tick applies its commands in order. The transfer command checks identity/account and exact generation, alive state, no attack/chase/swing/cooldown or incoming engagement, distance within 3 tiles of Class Master at (126, 128), current class as direct parent of the target, matching race, level 20/40, target tier ≤ 2 and supported typed-token requirements. Only after those checks pass does it mutate class/resources/learned metadata, consume one token and emit the internal ZoneEvent::ClassTransfer. A rejected command leaves progression and tokens unchanged.

5. Durable replay log admission: DurableTickGate::admit appends the AppliedTickRecord to the JetStream replay log and awaits acknowledgment. A new transfer cannot release output or RPC success before this acknowledgement and the following database commit.

6. Revision-fenced atomic Postgres checkpoint: The checkpoint worker executes an atomic database transaction: updates character progression and character_class_slots (slot 0), decrements token counts, upserts monotonic learned skills in character_learned_skills, stores the full immutable result in idempotency_keys and its permanent reference in character_transfer_receipts, and stages a CharacterClassChanged domain event in the transactional outbox. The transaction is revision-fenced (WHERE revision = revision_seen). A transient retry retains the same draft and holds subsequent drafts; permanent, stale, or missing lane conditions fail closed without success. Zone recovery reconciles the contiguous durable prefix before new admissions.

7. Public output release: After BOTH the JetStream log ack and the Postgres transaction commit succeed, the zone actor broadcasts ZoneEvent::ClassChanged to AOI observers, sends updated stats to the character owner, and returns the successful gRPC ChangeClassResponse.

Idempotency and historical isolation: Replaying a frozen idempotency receipt returns the exact historical response (e.g. class 1) even if the character subsequently advanced to class 2, without altering or reverting live projection. Character creation remains strictly at (0, 0); coordinates (126, 126) belong solely to isolated test fixtures. No milestone grants are triggered during class transfer. RPC completion is an application acknowledgement, not standalone worldstate; data checkpointed consists of progression and ledger facts rather than an open event schema.
