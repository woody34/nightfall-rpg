**B13 Paired Transfer Rule and Rule T1 (Amends Phase 4 D67/D69/D76 for V7; E26):**
An `ItemInstanceId` NEVER changes when an item changes owner (trade, pickup/drop, warehouse, freight, mail, vendor buy/sell). The ledger records a PAIRED transfer in one of three pinned modes:
- **identity mode:** whole count, and target has no stack: source `transfer_out` (after = None), target `transfer_in` (same ID, before = None).
- **merge mode:** stackable, and target holds stack: source `transfer_out`, target `transfer_in` on existing stack (`count_delta = +n`).
- **split mode:** partial count, and target has no stack: source `transfer_out` (after = count - n), target `transfer_in` on fresh ID (before = None).

Both rows carry `transfer = {link: UUIDv5(NS_XFER, resolution_id ‖ ordinal), mode, peer_owner_kind, peer_owner_id, peer_instance}` and the same receipt or cause. In identity mode, canonical fields are identical across the pair. A `transfer_in` with before = None is exempt from D67's "never seen earlier" rule ONLY when its link points to a matching identity `transfer_out` (B13).
Non-character owners hold explicit owner identities in the ledger:
- Ground items: `owner_kind = ground`, `owner_id = entity_id` (drop: player `transfer_out` -> ground `transfer_in`; pickup: ground `transfer_out` -> player `transfer_in`).
- Refund tab: `owner_kind = refund`, `owner_id = character_id`.
- Warehouse / Freight: `owner_kind = warehouse` / `freight`, `owner_id = character_id`.
- Mail: `owner_kind = mail`, `owner_id = message_id`.
- Auction bid escrow: `owner_kind = auction_bid`, `owner_id = UUIDv5(NS_AUCTION, auction_id ‖ character)`.
- Deliveries: `owner_kind = delivery`, `owner_id = delivery_id`.

**Rule T1 (Ratified by E26):** Per `(owner, tick, instance)`, ledger rows are ordered strictly:
1. all non-consume, non-terminal rows (positive grants, merges, `transfer_in`, equip/unequip, split `transfer_out` with count > 0);
2. the single Consume aggregate, if any;
3. at most one terminal row: `transfer_out` with after = None, or `destroy`.

**Lease Locking Rules, Ordering and Schema (E34, E38, E39, E42, design §10.0):**
- **Leases are the ONLY lock (E39):** There are **no** `SELECT … FOR UPDATE` data-row locks. Under E31 nobody but a lease holder writes the covered rows, and a lease release commits atomically with the holder's data, so a `READ COMMITTED` read taken after leases are inserted sees every committed checkpoint. If any key is already leased, refuse with `CONTAINER_BUSY` (retryable) and insert none.
- **Transient failures (E39):** Postgres deadlock (`40P01`) and serialization failures (`40001`), in a preflight or a checkpoint transaction, are classified **TRANSIENT**: the preflight returns `CONTAINER_BUSY`, and the checkpoint retries at the next cadence with the same acknowledged draft. They are never the permanent constraint fence.
- **Canonical key string & collation (E42):** Lease keys use `<owner_kind>:<39-digit zero-padded decimal owner_id>`, compared bytewise with Postgres column `COLLATE "C"`. Roles never decide order (sender vs receiver ordered strictly by ID).
- **Lease sets per command (E38; DR5 P2-2, design §10.0):** Acquired all-or-nothing in ascending bytewise key order:

- **Fresh row coverage:** A freshly inserted row is covered by the lease of the key under which it is inserted, recorded in `econ_container.lease`. A delivery row and its re-homed item rows are inserted under the delivery's **own** `delivery:d` key (UUIDv5), fencing early `DeliverPending` on that ID until the creating commit releases it (DR6 nit 5).
- **Mailbox count leases (E34):** Every inbox/outbox-modifying command leases the `mailbox` key, and `MailSend` freezes the recipient inbox count under it so the 240 capacity cannot be exceeded by racing zones.
- **System jobs refused CONTAINER_BUSY (E38):** The scheduler re-queues the job to the zone's **next tick** holding nothing (no lease and no admission slot).
- **Lease recovery and commit markers (DR6 nit 10, E42):** Unacknowledged commands have leases released by epoch-fenced recovery. Client intents key on client receipts. System jobs key on committed markers:
  - `DeliverPending`: delivery `status = 'delivered'`;
  - `AuctionSchedule`: auction row is in target state (or deleted for `Purge`);
  - `MailExpire`: message row is absent.
  A system job whose marker is absent has its leases released and is re-enqueued by the scheduler.

**Single Zone-Side Writer for Container Rows (E31):**
ALL writes to lease-governed container rows go through the owning zone's leased checkpoint transaction path. No RPC or background processor writes them directly:
- `MailMarkRead` is a WebSocket intent (CM 69 / PbCommandKind 72) handled by the zone actor; `ReadMail` is strictly read-only.
- Mail expiry is delivered as system command `MailExpire` (PbCommandKind 76): the zone re-homes attachments to a `delivery` owner before deleting expired rows.
- Unclaimed auction bids are purged via `AuctionSchedule{Purge}` (PbCommandKind 74, leasing `auction:<a>`) in the zone's checkpoint transaction, committing `destroy` rows for escrowed adena and deleting bid/auction rows atomically.

**Pending Deliveries & Queue Bound (E27, E41, rule P19):**
Cross-zone and offline credits—COD adena payments, mail-expiry attachment returns, and auction award items—are written to `economy_deliveries` under owner kind `delivery`.
**E41 amends E27:** Deliveries for one target run as a delivery-id queue, at most one per target per tick. Each completes within one checkpoint cadence after reaching the head of that target's delivery-id queue, and only the lowest-id delivery runs in the D7 admission slot.
When the recipient zone checkpoint runs, system command `DeliverPending` (PbCommandKind 73) executes the delivery into the target's inventory or warehouse with at most one checkpoint cadence of delay, emitting no `EconomyResult` (§10.4). `DeliverPending` leases `delivery:d` and `warehouse:c_target` (for warehouse destination) and freezes the destination warehouse pre-image with the pinned stackable merge rule (E33).

**Replay Independence and Frozen Transport (E12, E14, E17, E33):**
Every in-world economy mutation is a WebSocket intent (29..69) handled directly by the zone actor while the player is admitted (E14). RPCs are request/response reads (§13.4). Every lease-bound mutation freezes its DB-derived inputs into `PbCommandKind` payloads (32..76) so that replay never reads the database:
- `PbCommandKind::WarehouseDeposit(59)` / `WarehouseWithdraw(60)`: frozen container pre-image `{revision, rows[]}`.
- `PbCommandKind::FreightSend(61)`: frozen target same-account status and freight pre-image; `FreightWithdraw(62)`: own freight pre-image.
- `PbCommandKind::MailSend(63)`: frozen recipient resolution `{receiver_id or not_found, is_self, blocked}`, sender/receiver counts, `message_id`.
- `PbCommandKind::MailTakeAttachments(64)` / `MailReject(65)` / `MailCancel(66)` / `MailDelete(67)` / `MailMarkRead(72)`: message pre-image(s) incl. attachment rows and DB-time `expired`.
- `PbCommandKind::ManorBuySeed(68)` / `ManorSellCrop(69)`: production/procure row pre-images, manor mode, seed-crop reward resolution.
- `PbCommandKind::ItemAuctionBid(70)`: auction row, actor's bid row, `remaining_le_10min`.
- `PbCommandKind::ItemAuctionCancelBid(71)`: all non-CREATED auction rows with actor's bids and `older_than_14d`.
- `PbCommandKind::DeliverPending(73)`: delivery row plus source container pre-images; for warehouse destination, frozen warehouse pre-image `{revision, rows[]}` with stackable merge rule (E33).
- `PbCommandKind::AuctionSchedule(74)`: auction row, fixture item index, transition; for Finish, winner bid and escrow rows (E33); for Purge, all bid and escrow rows.
- `PbCommandKind::EpochReconcile(75)`: abandoned-epoch ground/refund manifest.
- `PbCommandKind::MailExpire(76)`: message pre-image, derived `delivery_id`.
No `NOW()` or `BIGSERIAL` values enter zone state: simulation uses zone ticks and monotone `ItemInstanceId`s only.

### 2.7 Domain rules

- **Monster drop resolution:** At monster death, killer is determined as `maxDealer`: the player within PartyRange 1600 L2 units (50,000 milli-tiles) who dealt damage > 1 (`GJ/model/actor/L2Attackable.java:341-379`). Deterministic tie-break: earliest damage dealt tick, then EntityId ordinal. Fallback to `lastAttacker` if maxDealer is null OR offline (`:357-377`). Level gap `d = mobLevel - killerLevel` evaluated via binary64-emulated killer modifier (E30, §3.3).
- **Level-gap window:** Grouped items (including all 2,309 adena entries, verification A29) use the 5/10/10% item window (`IKillerChanceModifierStrategy.java:33-43`, `GC/npc.properties:187-219`). Full chance until `d >= -5`; linear reduction to 10% floor at `d <= -10`. Binary64-emulated (E30).
- **Ground item identity & decay:** Ground items are zone entities with `EntityId` and incarnation carrying `item_instance_id: ItemInstanceId` (B5, EntityKind 3, EntitySpawn 30 GroundItemDetail). Snapshot-only state, not database tables (A15). Normal mob drops and raid drops are protected for 15,000 ms (15 s) to killer and killer's party (`L2Npc.java:1476-1478`, `ItemTable.java:214`, E7).
